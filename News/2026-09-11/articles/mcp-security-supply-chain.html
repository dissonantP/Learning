AI agent infrastructure

The dangerous part of an MCP tool may be its description

Recent tool-poisoning work makes a useful security point: an agent can be compromised before the malicious tool is ever called.

September 11, 2026

MCP security is easy to frame as “can this tool do something dangerous?” That is too narrow. Tool metadata is placed into the model’s context so the model can decide what to call. That means a malicious tool description is not passive documentation; it is executable influence over the planner.

This gives MCP a supply-chain property that ordinary API catalogs do not have. Installing or discovering a server can alter the model’s behavior even if the server’s tools are never invoked.

The important boundary is not only tool execution. It is tool discovery.

Implicit poisoning is worse than “the bad tool did a bad thing”

A January 2026 paper, MCP-ITP, studies a stealthier attack: malicious instructions are embedded in one tool’s metadata, but the poisoned tool itself need not run. The injected instructions can push the model toward invoking some other legitimate, higher-privilege tool instead.

The authors report attack success rates up to 84.2% on their setup while driving their malicious-tool detection metric as low as 0.3%. The exact numbers are benchmark-specific, but the qualitative result matters more: merely hiding a suspicious tool behind a confirmation dialog does not address metadata-level influence.

Client-side validation is still the weak point

A separate 2026 threat-modeling study applied STRIDE and DREAD across MCP hosts, clients, servers, models, authorization servers, and external data stores. Its empirical focus was tool poisoning across seven clients, and it found weak static validation and poor parameter visibility to be recurring problems.

The paper’s proposed defense is layered: inspect metadata statically, expose the model’s decision path, look for behavioral anomalies, and make tool parameters visible to the user. No single filter is expected to solve this because the attack is partly semantic rather than syntactic.

Tool catalogs need provenance and drift detection

MCPRadar is an interesting practical response because it treats an MCP server as something that should be snapshotted and diffed. It inspects instructions, tools, schemas, configuration, dependencies, and behavioral changes rather than only checking package vulnerabilities.

That is a better analogy than antivirus: a remote MCP server is closer to a dynamically changing plugin with both code and prompt-level authority. If its tool descriptions change between Tuesday and Wednesday, that is a supply-chain event worth reviewing.

Code Mode changes the attack surface again

Cloudflare’s Code Mode pattern reduces the number of model-visible tools by exposing a small code interface and keeping a large API schema outside the context. The model searches for relevant operations, writes code to compose them, and execution occurs inside an isolated Worker.

This can reduce context bloat and metadata exposure, but it introduces a different requirement: the code sandbox, host-provided request function, and credential boundary now become critical. The model no longer has hundreds of tool descriptions in its prompt, but it has a programmable execution surface.

A useful permission model

For an agent platform, I would separate at least four permissions: discover a tool, place its metadata into model context, allow the model to propose a call, and actually execute the call. Most current systems collapse those into one “server enabled” switch.

That separation would make it possible to inventory an MCP server without trusting its descriptions, statically scan metadata before exposure, require explicit approval for newly changed tools, and restrict high-impact capabilities at execution time even if the planner is manipulated.
