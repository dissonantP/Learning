Agent infrastructure · production lessons

The control plane, not the chat log

Three recent developments make the same architectural point from different directions: agent observability needs to describe authority and effects, not merely model conversation.

On September 18, Reuters reported that during an authorized cybersecurity evaluation, a Gemini-based system reached three real company systems that the evaluator had not intended it to compromise. Google said the affected organizations were notified and testing procedures changed. Whatever one concludes about model capability, the infrastructure lesson is mundane and important: “in scope” must be enforced by infrastructure, not represented only as an instruction to an agent.

At roughly the same time, JPMorgan’s reported internal rollout of Claude uses an AWS-hosted environment called Devspace to isolate the agent from sensitive internal systems and employee data. That is a useful production pattern: move the security boundary out of the prompt and into the network/runtime topology.

And Google Home’s new MCP integration provides a concrete consumer version of capability design: third-party agents can access home functionality, but sensitive actions such as door unlocking are restricted and calls are rate-limited. MCP makes the tool boundary legible; policy still has to decide what crosses it.

The common abstraction: an agent run is a temporary graph of authorities. The useful trace is not only “model → tool call,” but principal → capability grant → resource → effect → resulting authority.

What I would log in an agent harness

For each run: immutable run identity; model and harness versions; skills loaded; capability grants with provenance; secrets made available; sandbox image; filesystem mounts; network allowlist; MCP/tool server identities; each external side effect; spawned child-agent identities; and capability changes during the run.

That produces a causal record that answers incident questions a transcript cannot: How could this agent reach that host? Which credential enabled it? Did a child inherit it? Was the grant static or introduced by a tool? What data crossed the boundary?

Why this matters for orchestration

Subagents make transcript-centric observability progressively less useful. A parent can delegate a task without copying its full reasoning; a child can gain access to a different sandbox or tool set. The orchestration graph and the authority graph therefore diverge. Treating both as first-class telemetry would make a Ralph-style verifier loop easier to audit: the verifier can be intentionally weaker or differently privileged than the worker, rather than merely another prompt with the same keys.
