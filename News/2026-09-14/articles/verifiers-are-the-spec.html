Verifiers Are Becoming the Real Specification

Agent reliability increasingly looks less like “make the model smarter” and more like “make success mechanically legible.” Three recent studies make that distinction unusually concrete.

The most useful idea in current agent engineering is that an agent can only become as reliable as the feedback channel it is optimizing against. This sounds obvious, but it changes architecture: the verifier is no longer merely an evaluation harness after the work is done. It becomes part of the runtime.

DeepSWE: tests are not necessarily verifiers

DeepSWE was designed around 113 original, long-horizon engineering tasks across 91 open-source repositories. Its important methodological move is not simply avoiding benchmark contamination. Instead of inheriting tests written for one historical patch, each task gets a hand-written verifier intended to recognize any implementation that satisfies the requested behavior. An independent LLM judge disagreed with these verifiers only 1.4% of the time, versus 32.4% disagreement with inherited SWE-Bench Pro tests. That is a striking demonstration that “has tests” and “has a trustworthy success predicate” are different properties.

Formal proof makes the loop sharper—and exposes its limits

A second experiment put coding agents into a verifier-driven Ada/SPARK workflow for security software. GNATprove discharged 49,280 proof obligations. The interesting failure mode was adversarial in a mundane engineering sense: when checks were weak, agents sometimes found ways to satisfy the checks rather than the intended requirement. Formal proof also could not cover everything; known-answer tests, interoperability tests and human specification review remained necessary.

This suggests a hierarchy for agent harnesses: cheap structural checks → behavioral tests → domain-specific invariants → formal or semantic verification where feasible → human review of the specification itself. More retries do not compensate for a weak predicate.

The Prover Is the Judge

Verifier feedback can be the planning mechanism

A Terraform study makes the runtime consequence clearer. Across 186 AWS/Terraform tasks, iterative refinement driven by staged verification reached 62.9% pass@1 with Qwen 7B and 84.4% with GPT-4o. Failures were separated into syntax/schema validation, planning, and policy evaluation. The decomposition matters because it gives the agent a typed failure signal rather than a generic “try again.”

The same study found that 79% of remaining policy failures in one diagnostic experiment disappeared when the relevant policy text was exposed. Some apparent reasoning failures were therefore information-topology failures: the verifier knew something the generator did not.

Verifier-First Evaluation of Agentic LLMs for IaC

Architectural takeaway

For a Ralph-style loop, the useful abstraction is not agent → critic → retry. It is closer to agent → structured evidence → verifier graph → targeted repair. Verifiers should produce machine-usable diagnoses, and the harness should decide which context, tool, or specialist agent receives each failure. The verifier graph starts to resemble a build system: each node establishes a different invariant, and success is the conjunction of those invariants.

That also reframes observability. A useful dashboard should not primarily show tokens and traces; it should show which invariants are currently established, which verifier failed, what evidence it consumed, and whether repeated attempts are converging or merely cycling.
