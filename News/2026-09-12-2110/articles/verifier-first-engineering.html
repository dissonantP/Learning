Verification

Verification is becoming the product

The hard part of coding agents is shifting from generation to proving that generated work is acceptable.

A cluster of recent work points in the same direction: generation quality is no longer the only interesting variable. The more consequential question is whether an agent can satisfy policy, survive tests, integrate cleanly and do so within a bounded cost and review budget.

A September survey paper frames this as a “verification tax”: agentic systems may produce more code while moving the bottleneck downstream into review, CI, security and integration. Its useful contribution is not a new benchmark but a systems view: measure production-qualified change rather than raw output.

That framing is reinforced by verifier-first experiments. In infrastructure-as-code generation, iterative verifier feedback substantially improves pass rates because the model can see concrete failures from validation, planning and policy checks rather than guessing from prose. A separate coding-agent study on open-source contribution rules finds that agents rarely retrieve repository rules proactively; explicit reminders and verifier feedback help with disclosure and verification gates, but some policies still fail systematically.

What this suggests

For long-running coding agents, the verifier should be treated as an independent subsystem, not a final prompt. It can combine executable tests, repository policy, static analysis, security checks, budget constraints and human-escalation rules. The outer loop should optimize for “accepted change” rather than “agent says done.”

This also changes observability. The important event stream is not just tool calls; it is why a run was rejected, what evidence changed the next attempt, how many retries were needed, and which policies repeatedly fail. Those failure classes become inputs to better harness design.
