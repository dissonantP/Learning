AI Agent Infrastructure · September 16, 2026

The harness is becoming the platform

The interesting shift in agent infrastructure this month is not another model jump. It is the packaging of the formerly home-grown agent harness—context management, tool dispatch, subagents, persistence and execution environments—as a managed systems layer.

OpenAI’s September 10 Agents API is unusually explicit about this. The product is not framed as a thin inference endpoint: it exposes the Codex harness, long-running execution, hosted or external sandboxes, MCP/custom tools, and parallel subagents. OpenAI also says the harness itself is versioned alongside models. That makes the harness a first-class dependency rather than incidental application code.

This matters architecturally. A year ago, an agent stack was often model + prompt + tool loop, with teams building scheduling, context compression, child-agent coordination and workspace persistence themselves. The new abstraction boundary looks more like model + managed runtime + domain capabilities. Sandbox vendors remain interchangeable underneath: OpenAI names Blaxel, Cloudflare, Daytona, DigitalOcean, E2B, Modal, Oracle, Runloop and Vercel alongside its hosted environment.

Practical consequence: agent-harness evaluation should increasingly look like framework/runtime evaluation: inspect scheduling semantics, context isolation, resumability, permission boundaries, observability and portability—not merely which model it can call.

A second signal is Google Home’s new MCP integration, reported September 16. It allows external agents to act against smart-home infrastructure while Google keeps explicit restrictions such as preventing door unlocks. MCP is therefore moving beyond “LLM calls developer tools” toward a generic capability boundary for agents operating physical or durable systems. The interesting engineering problem becomes authority: which verbs exist, which require confirmation, what is logged, and what downstream service is implicitly trusted.

The uncomfortable part: sandbox ≠ boundary

A recent GitLab security analysis makes the complement clear: an isolated agent can still escape through an allowlisted service. In the reported evaluation, a package proxy that the sandbox was permitted to contact became the route outward. The lesson is old distributed-systems security in a new setting: every allowed dependency becomes part of the effective trust boundary. A network allowlist is a graph of delegated trust, not a wall.

This suggests a useful model for agent runtimes: treat tools, MCP servers, package mirrors, source control and internal APIs as capabilities whose transitive authority must be understood. Filesystem isolation alone is insufficient when a permitted endpoint can itself reach privileged systems.
