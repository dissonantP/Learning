AI agent infrastructure · architecture

The agent loop is not the runtime

A useful 2026 convergence: orchestration state, model reasoning, and code execution are being pulled apart. That separation makes long-running agents easier to secure, resume, observe, and swap across compute backends.

A lot of early agent systems treated the whole agent as one process: model loop, tool calls, files, credentials, browser, shell and state all co-located. That is convenient for prototypes and awkward for everything else. Recent platform work from OpenAI, Cloudflare, Anthropic integrations and sandbox vendors increasingly treats the harness as a control plane and execution as a disposable data plane.

What the split buys you

The harness can own durable conversation state, task queues, retries, approvals and model calls while an execution sandbox is created only when needed. The sandbox gets a narrow filesystem, network policy and temporary credentials; it can then be snapshotted, killed, replaced or moved to another provider without destroying the agent's higher-level state.

Architectural consequence: persistence no longer implies persistent compute. A task can live for hours or days while the machine that performs any individual action lives for seconds or minutes.

Cloudflare's Project Think makes this explicit with durable execution, subagents, sandboxed code execution and persistent sessions as separate primitives. OpenAI's updated Agents SDK similarly describes decoupling the harness from compute for security, durability and scale. Modal's integration with Claude Managed Agents pushes the same boundary another way: Anthropic hosts the agent loop while tool execution occurs in a user-controlled Modal sandbox.

Security becomes a routing problem

Once execution is externalized, permissions can be attached to each run instead of inherited from a monolithic process. A research subagent may receive read-only network access and no secrets; a deployment agent might receive one short-lived credential and a single outbound target. The orchestrator becomes the place where capabilities are granted, logged and revoked.

This also improves observability. A sandbox boundary gives a natural trace unit: input state, filesystem snapshot, tool calls, network attempts, outputs and exit status. That is much easier to reason about than a single long-lived agent process whose state slowly accumulates.

What this suggests for self-hosted agent stacks

The useful abstraction is not “one container per agent.” It is closer to one durable task graph + many replaceable execution environments. The orchestrator should survive worker death; sandboxes should be reconstructible; credentials should be injected at execution time; and human approval should sit above both.

This is also why session trees and subagents become more meaningful when they are first-class orchestration objects rather than just subprocesses. A parent can keep the logical relationship while children execute in entirely different sandboxes.
