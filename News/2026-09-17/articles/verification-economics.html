Agent infrastructure · Verification

Agent throughput moves the bottleneck downstream

When generation becomes cheap, review, integration, CI, security and human attention become the scarce resources. That changes what an agent harness should optimize.

A recent synthesis, Beyond Code Generation, proposes a useful unit: “production-qualified change.” Instead of counting code written, tasks attempted or even tests passed, ask how much change survives review, integration, security checks and deployment per dollar and per reviewer-hour. The paper is a synthesis rather than a new controlled experiment, so its numerical claims inherit the limitations of the underlying studies. But its framing is useful for harness design.

Agents turn a sequential development loop into a queueing problem. If four subagents can produce candidate changes concurrently while one human reviews them, generation throughput can rise while system throughput stays flat. Worse, low-quality parallel work increases the review queue. The correct scheduler therefore should not maximize active agents; it should allocate autonomy against downstream capacity.

The verification tax is not overhead

Tests, graders, linters, policy checks, sandbox runs and critic passes are often described as an added “verification tax.” But once generation is abundant, they are the mechanism that converts generated work into trusted work. The interesting engineering problem is selective verification: cheap deterministic checks first, expensive model-based or human review only where uncertainty remains.

This suggests a harness architecture closer to a build system. Each task carries an evidence bundle: patch, tests, execution traces, verifier results, capability grants and unresolved uncertainty. The orchestrator can then decide whether to retry, escalate, merge, or ask for human input based on evidence rather than agent confidence.

The scarce resource in a multi-agent system may not be tokens or compute. It may be the number of ambiguous decisions a human can responsibly resolve per hour.

A scheduler worth building around

For a persistent multi-project setup, the scheduler can expose three budgets explicitly: compute/token budget, verification budget, and human-attention budget. A task that has exhausted cheap verification but still has a narrow ambiguity should queue for human input; a task with broad test failure should be recycled automatically; a task whose permissions exceed its expected value should remain blocked. That makes “human in the loop” a routing decision rather than a modal interruption.
