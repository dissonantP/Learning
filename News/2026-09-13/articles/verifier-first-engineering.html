AI agent infrastructure · verification

Verifier-first engineering

The interesting shift is not “agents can retry.” It is that the verifier is becoming part of the architecture: an explicit, independently designed system that determines what counts as progress.

Agentic coding often gets described as a loop: generate, test, inspect failures, retry. That framing hides the hard part. The loop only works if the feedback channel is trustworthy enough to distinguish a genuinely correct result from a locally plausible one.

Three recent results point in the same direction

DeepSWE built 113 original, long-horizon engineering tasks and graded them with handwritten verifiers rather than inherited repository tests. Its authors report that an independent LLM judge disagreed with DeepSWE's verifier on only 1.4% of runs, versus 32.4% disagreement with SWE-Bench Pro's inherited tests. The implication is uncomfortable but useful: benchmark quality can be dominated by the quality of the verifier rather than by the prompt or model.

Verifier-First Evaluation of Agentic LLMs for IaC decomposes Terraform success into validate, plan and policy-evaluation stages. Iterative refinement with verifier feedback pushed pass@1 to 62.9% for Qwen 7B and 84.4% for GPT-4o on its benchmark. More interestingly, many remaining failures were information-gap failures: once policy text was made visible, a large fraction disappeared.

Glite ARF moves the same idea from evaluation into orchestration. Rather than trusting agents to remember process constraints, deterministic Python verifiers enforce task isolation, immutability and provenance. The authors ran up to twelve parallel coding agents over hundreds of tracked tasks and used the verifier layer to catch target leakage that otherwise produced implausibly good results.

General pattern: encode process invariants in executable checks whenever possible. Instructions tell an agent what you want; verifiers define what the system will accept.

The verifier is a product surface

For a practical agent stack, this suggests treating verifiers as first-class modules with their own versioning, logs and failure taxonomy. “Tests failed” is too coarse. A useful verifier should answer: did the artifact build, did behavior match intent, were policy constraints satisfied, did the agent mutate forbidden state, is the result reproducible, and is there enough evidence to trust the claim?

This also changes how human review is used. The human does not need to inspect every action. Instead, human attention can be concentrated on cases where deterministic checks are weak: ambiguous intent, visual quality, risky external actions, or verifier disagreement.

A more useful loop

Rather than agent → tests → retry, think agent → evidence production → layered verifiers → diagnosis → targeted retry. That makes the verifier responsible not only for saying “no,” but for generating structured evidence the next attempt can use.
