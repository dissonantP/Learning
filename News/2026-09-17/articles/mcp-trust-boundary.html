Agent infrastructure · Security

The tool server is part of your security perimeter

MCP made tools composable. The uncomfortable consequence is that a tool description, a server response and a skill package are now all executable influence over the agent. Recent security work converges on a useful design rule: admission, authority and execution need separate boundaries.

The most interesting shift in agent security is away from asking whether a model is “safe” and toward asking what authority the runtime can actually exercise. MCP Security Bench models twelve attacks across the tool-use lifecycle—including tool-name collision, malicious descriptions, parameter overreach, user impersonation and cross-tool transfer. Its dataset is executable rather than a bag of prompts: more than 2,000 attack instances, 405 tools and 65 tasks run through actual MCP plumbing.

That matters because protocol composition creates failure modes that are not visible when a model and a tool are tested independently. Breaking the Protocol reports experiments over 847 scenarios and five server implementations; the authors attribute substantially higher attack success to MCP-specific trust propagation and unauthenticated capabilities. The exact numbers deserve replication, but the architectural point is stronger than any one benchmark: interoperability standardizes the attack surface as well as the interface.

Admission is not authorization

Attested Tool-Server Admission makes a distinction that maps cleanly onto ordinary distributed systems. First decide whether a server identity is admitted. Then independently decide which of its tools are allowed. The proposed extension uses offline-signed clearance assertions, pinned trust roots and deny-by-default per-server allowlists, with enforcement decisions written to a tamper-evident log.

This is closer to capability security than the common “connect this MCP server” UX. Trusting a server does not imply trusting every capability it advertises, and discovering a new tool should not silently enlarge the agent's authority. The same principle suggests storing tool-set/version state in the execution trace: a replay is not meaningful if the available capability surface has drifted.

Skills are a hybrid supply chain

MalSkillBench exposes another awkward boundary. Agent skills can contain natural-language instructions, scripts and permissions simultaneously. Its 3,944 runtime-verified malicious skills show why conventional package scanners and prompt-injection filters each see only half the object. The authors report strong detection for code injection but much weaker performance on prompt injection and attacks on the agent control plane.

A useful mental model: an agent extension is neither “prompt” nor “package.” It is a principal that can alter planning and execution. Review it at both layers.

What this implies for a practical harness

A production harness can treat the boundary as four explicit decisions: identify the server or skill; attest the artifact/version; grant only named capabilities for the task; and record every grant plus resulting action in the trace. Sandboxing then limits consequences when all three upstream judgments fail. This also makes human approval more meaningful: “allow filesystem.write for this task” is a comprehensible approval; “trust this agent” is not.

There is a timely real-world sign that this is becoming operational rather than theoretical. JPMorgan is reportedly rolling out an AWS-hosted “Devspace” that isolates Claude from sensitive internal systems and data. Meanwhile AGNTCon + MCPCon is taking place in Amsterdam on September 17–18 with production reliability and security as explicit program themes. The stack is starting to look less like chatbot middleware and more like a small distributed operating system.
