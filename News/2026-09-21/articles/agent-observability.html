The trace is becoming the product

Agent observability is moving beyond “log the prompt and tool call.” The interesting work now treats plans, delegation, memory, policy decisions and side effects as first-class events—and asks whether a run can be replayed and audited.

Conventional distributed tracing is a poor fit for agents because the causal structure is richer than service A calling service B. An agent may formulate a plan, retrieve memory, delegate, revise the plan, call a tool, encounter a policy gate and create an external side effect. AgentTelemetry, published in the 2026 ACM AIware proceedings, makes this concrete: it argues that current OpenTelemetry GenAI conventions omit span-level representation for planning, reasoning, safety monitoring, inter-agent delegation and memory management.

That suggests a useful design rule: instrument the control plane, not just the model API. IBM researchers make a related argument in Formalizing Observability in Agentic AI Systems: system behavior can emerge at agent–agent and agent–environment interfaces, so observability layers belong at those boundaries rather than only around individual models.

From telemetry to evidence

A more ambitious 2026 proposal, Trace-Based Assurance for Agentic AI Orchestration, models executions as Message-Action Traces. Each step can carry machine-checkable contracts; violations can be localized to the first bad step; runs can be deterministically replayed; and retrieval, service and memory boundaries can be fault-injected. The important conceptual shift is that a trace is not merely diagnostic exhaust. It becomes the evidence that an action was allowed, correctly mediated and contained.

Practical implication: for an agent harness, persist an immutable event stream containing parent/child causality, model and prompt identity, tool arguments/results, delegation, memory reads/writes, policy verdicts, side effects, verifier verdicts and artifact hashes. Derive the UI from that stream. This gives replay and audit a common substrate.

Scale breaks discovery before reasoning

Autonomous Event-Driven Multi-Agent Orchestration for Enterprise AI at Scale tested DAG Plan-and-Execute and ReAct across 208 production-derived scenarios from fewer than ten to 200 agents. Its surprising result is that scale rather than task complexity dominates degradation: agent-discovery noise becomes a bottleneck, and simple tasks can degrade more sharply than complex ones. Their event Task Manager uses priority inference, related-event merging and preemption; reported high-priority queue latency improved by 14–75%.

A separate hierarchical orchestration proposal attacks the same problem by abandoning a flat capability registry. Tools are organized into a tree and discovered lazily; a stack records nested execution contexts. Whether or not that exact architecture wins, both papers point to the same systems lesson: tool/agent discovery is itself an orchestration subsystem. A huge tool list in a prompt is not a scalable registry.

One architecture worth stealing

Put these results together and a clean harness architecture appears: event ingress → scheduler/task manager → hierarchical capability discovery → execution → policy mediation → verifier → append-only trace. The LLM is then one component inside a deterministic-ish control plane rather than the control plane itself.

That separation also makes failure semantics clearer. A model can be stochastic while the surrounding system still has explicit identities, deadlines, budgets, permissions, idempotency keys, retry policy and replayable history.
