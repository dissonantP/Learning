The agent boundary is moving

The interesting security unit is no longer the model. It is the model plus harness, installed skills, workspace, credentials and runtime policy.

Two 2026 security benchmarks make essentially the same architectural point from different directions. AgentTrap tests third-party agent skills and finds a subtle failure mode: agents can satisfy the visible user request while accepting unsafe side effects hidden inside an apparently ordinary skill workflow. Its 141 tasks model skills as a software supply chain, not merely prompts.

GrantBox goes one level lower and gives agents real privileges over real tools. Under carefully designed prompt-injection scenarios, the reported average attack success rate is 84.8%. The important distinction is ecological validity: evaluating a model's refusal behavior is not equivalent to evaluating a deployed agent's privilege behavior.

Capability security is becoming concrete

This pushes agent architecture toward familiar operating-system ideas: scoped identities, least privilege, mediation at every tool call, and auditable traces. Anthropic and Google Cloud's production session describes exactly that stack: per-agent identities, IAM policy, an agent gateway, runtime defenses and OpenTelemetry audit events.

MCP is moving in the same direction. The Enterprise-Managed Authorization extension, declared stable June 18, lets organizations centrally provision MCP access through identity providers. Meanwhile OAuth Client Credentials addresses unattended machine-to-machine agents directly.

Why this matters for a harness

A useful mental model is that an agent harness is becoming a small distributed operating system. Sessions are processes; tools are syscalls; MCP servers are network services; skills resemble packages; credentials are capabilities; traces are an audit log. The LLM is an unusually flexible scheduler and planner inside that system, but it should not itself be the security boundary.

That suggests a practical design test for orchestration systems: can permissions be attached to an individual spawned session, inherited or attenuated when it creates children, inspected independently of the prompt, and enforced outside the model? If not, the system still relies heavily on behavioral compliance.
