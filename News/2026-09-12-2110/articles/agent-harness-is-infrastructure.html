AI agent infrastructure

The agent harness is becoming infrastructure

Managed loops, sandboxes, subagents and observability are collapsing into a deployment layer.

OpenAI’s new Agents API is a useful marker of where agent engineering is moving: away from a model-plus-tools abstraction and toward a durable runtime that owns orchestration, long sessions, context compaction, subagents and execution environments. The API can run agents in OpenAI-hosted sandboxes, on a developer’s own infrastructure, or through partner sandbox providers. In other words, the harness itself is being productized as infrastructure.

This matters because it redraws the boundary between the “brain” and the “hands.” A model can remain ephemeral while the runtime persists task state, controls tool access, provisions compute, and decides where credentials live. That separation is also visible elsewhere: GitHub now exposes centrally managed sandbox policy in Copilot for JetBrains, including filesystem, network, proxy, developer-tool and Keychain restrictions.

The security implication is that sandboxing is not enough by itself. Anthropic’s September threat report describes attackers targeting AI credentials, evaluation sandboxes, proxies and scheduled agent jobs. The valuable boundary is the control plane around the sandbox: scoped credentials, policy checks, audit events, tool mediation and revocation.

A useful architecture

A practical pattern is emerging: keep orchestration state and credentials outside the execution environment; give workers short-lived or narrowly scoped capabilities; treat subagent creation as policy-bearing delegation; and make every external side effect observable. The sandbox is disposable. Authority should not be.

For self-hosted agent systems, that suggests a design closer to Kubernetes or CI than to a chat app: a durable scheduler/control plane dispatching work into disposable workers, with explicit capability grants and traces for each run.
